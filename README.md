# TCP และ UDP — Transport Layer (Layer 4)

## ภาพรวม

การส่งข้อมูลด้วย IP เพียงอย่างเดียว **ไม่ได้รับประกันว่าข้อมูลจะถึงปลายทางครบถ้วนหรือมาถึงตามลำดับเดิม** ดังนั้นระบบเครือข่ายจึงมีโปรโตคอลใน **Transport Layer (Layer 4)** เช่น **TCP (Transmission Control Protocol)** และ **UDP (User Datagram Protocol)** เพื่อรองรับรูปแบบการสื่อสารที่แตกต่างกัน

- **TCP** มีการตั้งการเชื่อมต่อก่อนส่งข้อมูล และมีกลไกติดตามการรับส่ง ช่วยให้ข้อมูลที่ส่งผ่าน TCP ถูกส่งมอบให้แอปพลิเคชันปลายทางอย่างครบถ้วนและเรียงลำดับตามที่กำหนด ตราบเท่าที่การเชื่อมต่อยังสามารถดำเนินต่อไปได้
- **UDP** ส่งข้อมูลได้โดยไม่ต้องตั้งการเชื่อมต่อก่อน และตัว UDP เองไม่มีการยืนยันการรับหรือส่งข้อมูลซ้ำให้อัตโนมัติเมื่อข้อมูลสูญหาย

ทั้งสองโปรโตคอลมีข้อดีและข้อจำกัดต่างกัน ไม่มีโปรโตคอลใดเหมาะกับทุกงาน

## 1. IP ส่งข้อมูลอย่างไร และมีข้อจำกัดอะไร?

### 1.1 IP เป็น Connectionless

**Connectionless** หมายถึง IP ไม่จำเป็นต้องตั้งการเชื่อมต่อกับปลายทางก่อนส่งแต่ละ Packet

เมื่อ PC ส่งข้อมูลไปยัง Server ข้อมูลจะถูกแบ่งเป็นหน่วยสำหรับการส่งผ่านเครือข่าย โดยในระดับ IP เรียกว่า **IP Packet** (คำว่า Packet ในบริบทนี้หมายถึงหน่วยข้อมูลของ IP)

Router จะอ่านข้อมูลส่วนหัวของ IP เช่น IP Address ปลายทาง แล้วเลือกวิธีส่งต่อโดยอาศัยตารางเส้นทางและสถานะเครือข่าย ณ เวลานั้น IP Packet ที่เป็นส่วนหนึ่งของการสื่อสารเดียวกัน **อาจเดินทางคนละเส้นทางได้** แต่ไม่ได้หมายความว่าทุก Packet จะต้องเปลี่ยนเส้นทางเสมอไป

### 1.2 ส่งก่อน ไม่ได้แปลว่าจะถึงก่อน

Packet แต่ละก้อนอาจใช้เวลาเดินทางไม่เท่ากัน เช่น เพราะเส้นทาง ความหนาแน่นของเครือข่าย หรือการประมวลผลระหว่างทาง จึงอาจมาถึงไม่เรียงตามลำดับที่ส่ง

```text
PC ส่ง:        Packet 1 → Packet 2 → Packet 3
Server ได้รับ: Packet 2 → Packet 1 → Packet 3
```

เลข 1, 2 และ 3 ในตัวอย่างนี้ใช้แสดงลำดับสมมติเท่านั้น **ยังไม่ใช่ค่า TCP Sequence Number**

หากโปรแกรมต้องการข้อมูลตามลำดับเดิม ต้องมีกลไกจัดการลำดับเพิ่มเติม เพราะ **IP ไม่รับประกันลำดับของ Packet**

### 1.3 สิ่งที่ IP ไม่รับประกัน

| เรื่อง              | ความหมาย                                                                         |
| ------------------- | -------------------------------------------------------------------------------- |
| การถึงปลายทาง       | Packet อาจสูญหายระหว่างทาง                                                       |
| ลำดับการมาถึง       | Packet ที่ส่งทีหลังอาจมาถึงก่อน                                                  |
| การส่งข้อมูลครบถ้วน | IP ไม่มีกลไกแบบ End-to-end เพื่อยืนยันว่าข้อมูลทั้งหมดจากการส่งนั้นได้รับครบแล้ว |

คำว่า **“ไม่รับประกัน” ไม่ได้หมายความว่าข้อมูลจะมีปัญหาทุกครั้ง** แต่หมายความว่าเราใช้ IP เพียงอย่างเดียวเพื่อยืนยันผลเหล่านี้ไม่ได้

IP และกลไกตรวจสอบข้อผิดพลาดระดับอื่นอาจช่วยตรวจพบปัญหาบางชนิดได้ แต่ IP เองไม่ได้ให้การรับประกันการส่งถึงและการเรียงลำดับแบบ TCP

## 2. TCP และ UDP อยู่ตรงไหนใน Network Model?

| Layer                   | หน้าที่หลัก                                                                 | ตัวอย่าง                         |
| ----------------------- | --------------------------------------------------------------------------- | -------------------------------- |
| **Layer 4 — Transport** | สื่อสารระหว่างปลายทางของแอปพลิเคชัน และจัดการข้อมูลตามความสามารถของโปรโตคอล | TCP, UDP                         |
| **Layer 3 — Network**   | ส่ง Packet ข้ามเครือข่ายโดยใช้ที่อยู่ IP                                    | IP, IPv4                         |
| **Layer 2 — Data Link** | ส่งข้อมูลผ่านลิงก์หรือเครือข่ายท้องถิ่นที่กำลังใช้งาน                       | Ethernet, PPP, Frame Relay       |
| **Layer 1 — Physical**  | ส่งสัญญาณผ่านสื่อจริง                                                       | สายทองแดง ใยแก้วนำแสง คลื่นวิทยุ |

### IP Address กับ MAC Address ต่างกันอย่างไร?

- **IP Address** ใช้ระบุปลายทางในระดับ IP เพื่อให้ Packet เดินทางข้ามเครือข่ายได้
- **MAC Address** ใช้ในการส่งข้อมูลผ่านลิงก์ Data Link เช่น Ethernet ภายในช่วงการส่งที่เกี่ยวข้อง

**Ethernet ครอบคลุมทั้ง Layer 1 และ Layer 2** ไม่ได้อยู่เฉพาะ Physical Layer ส่วน PPP และ Frame Relay เป็นตัวอย่างเทคโนโลยีที่เกี่ยวข้องกับ Layer 2 ของลิงก์ WAN

ในหัวข้อนี้ให้มองภาพรวมของแต่ละ Layer ก่อน แล้วค่อยเชื่อมเรื่อง Port Number และ Socket ในหัวข้อถัดไป

## 3. UDP — User Datagram Protocol

### 3.1 UDP คืออะไร?

UDP เป็นโปรโตคอลใน Transport Layer ที่ส่งข้อมูลได้โดย **ไม่ต้องตั้งการเชื่อมต่อก่อน** หรือเรียกว่า **Connectionless**

เปรียบเทียบได้กับการส่งจดหมายธรรมดา: ผู้ส่งส่งจดหมายออกไป แต่ระบบส่งจดหมายไม่ได้ทำให้ผู้ส่งได้รับคำยืนยันกลับมาโดยอัตโนมัติว่าผู้รับได้รับแล้ว

```text
โปรแกรมผู้ส่ง                         โปรแกรมผู้รับ
     │                                    │
     └────────── ข้อมูลผ่าน UDP ─────────>│

UDP เองไม่มี ACK ยืนยันการรับกลับมา
```

### 3.2 Encapsulation ใน UDP

**Encapsulation** คือการนำข้อมูลของแอปพลิเคชันมาห่อด้วยส่วนหัวของโปรโตคอล เพื่อให้ระบบรู้วิธีจัดการและส่งข้อมูลต่อ

ในกรณีของ UDP ข้อมูลจากแอปพลิเคชันจะถูกห่อด้วย **UDP Header** ซึ่งมีข้อมูลสำคัญ เช่น:

- **Source Port** — พอร์ตต้นทาง
- **Destination Port** — พอร์ตปลายทาง
- **Length** — ความยาวของ UDP Header และข้อมูล
- **Checksum** — ใช้ตรวจสอบข้อผิดพลาดของข้อมูลตามกลไกที่กำหนด

Encapsulation **ไม่ใช่การเข้ารหัสเพื่อปกปิดข้อความ** แต่เป็นการเพิ่มข้อมูลกำกับให้โปรโตคอลทำงานได้

### 3.3 UDP ไม่รับประกันอะไร?

ตัว UDP เองไม่มีการรับประกันว่า:

- ข้อมูลจะไปถึงปลายทาง
- ข้อมูลจะมาถึงตามลำดับที่ส่ง
- ข้อมูลที่สูญหายจะถูกส่งซ้ำให้อัตโนมัติ
- ผู้ส่งจะได้รับการยืนยันว่าผู้รับได้รับข้อมูลแล้ว

UDP อาจส่งข้อมูลถึงตามปกติได้ เพียงแต่การส่งออกไปไม่ได้แปลว่าผู้ส่งทราบแน่นอนว่าปลายทางได้รับแล้ว

### 3.4 ถ้าโปรแกรมใช้ UDP แต่ต้องการรู้ว่าข้อมูลถึงหรือไม่?

โปรแกรมสามารถออกแบบกลไกเพิ่มเติมเองได้ เช่น ให้ฝั่งรับส่งข้อความตอบกลับ

```text
โปรแกรมฝั่งส่ง                       โปรแกรมฝั่งรับ
     │                                    │
     ├──── ข้อความผ่าน UDP ──────────────>│
     │<──── “ได้รับแล้ว” ผ่าน UDP ─────────┤
```

ข้อความตอบกลับนี้เป็นกลไกที่ **โปรแกรมหรือโปรโตคอลระดับแอปพลิเคชันออกแบบเพิ่ม** ไม่ใช่การยืนยันที่ UDP ให้มาโดยอัตโนมัติ หากต้องการความสามารถอื่น เช่น ส่งซ้ำเมื่อไม่ได้รับคำตอบ จัดลำดับ หรือป้องกันข้อมูลซ้ำ โปรแกรมก็ต้องออกแบบกลไกเหล่านั้นตามความต้องการด้วย

### 3.5 Best effort

UDP มักอธิบายว่าเป็นการส่งแบบ **Best effort** กล่าวคือ IP/UDP พยายามส่งข้อมูลไปยังปลายทาง แต่ตัว UDP ไม่ได้เพิ่มกลไกยืนยันการรับและส่งซ้ำให้เอง

คำว่า Best effort ไม่ได้แปลว่า UDP พยายามน้อยกว่าเสมอไป แต่หมายถึง UDP มีหน้าที่และการรับประกันน้อยกว่า TCP ในด้านการติดตามการส่งข้อมูล

## 4. TCP — Transmission Control Protocol

### 4.1 TCP คืออะไร?

TCP เป็นโปรโตคอลใน Transport Layer ที่มีการตั้งการเชื่อมต่อและติดตามสถานะการรับส่งข้อมูล จึงเรียกว่า **Connection-oriented**

เปรียบเทียบกับการโทรศัพท์: คู่สนทนาติดต่อกันและมีการโต้ตอบก่อนเริ่มคุยตามปกติ อย่างไรก็ตาม TCP ไม่ได้หมายถึงการสร้างสายทางกายภาพใหม่ และไม่ได้บังคับให้ IP Packet ทุกก้อนเดินทางผ่านเส้นทางเดียวกัน

### 4.2 Three-way Handshake

TCP ใช้ขั้นตอนเริ่มต้นที่เรียกว่า **Three-way Handshake** เพื่อเริ่มการเชื่อมต่อและประสานข้อมูลควบคุมที่จำเป็นระหว่างสองฝั่ง

```text
Client                                      Server
   │                                           │
   │──────────── SYN ─────────────────────────>│
   │<─────────── SYN-ACK ─────────────────────│
   │──────────── ACK ─────────────────────────>│
   │                                           │
   │       เริ่มส่งข้อมูลตามการเชื่อมต่อ         │
```

- **SYN** — ใช้เริ่มต้นการเชื่อมต่อและเสนอค่าเริ่มต้นของ Sequence Number
- **SYN-ACK** — ตอบรับ SYN และส่ง SYN ของฝั่ง Server กลับ
- **ACK** — ยืนยันการตอบกลับ ทำให้ขั้นตอนตั้งต้นครบสามช่วง

การ Handshake มีการแลกเปลี่ยนข้อมูลควบคุมก่อนส่งข้อมูลตามปกติ จึงเป็นส่วนหนึ่งของ **Overhead** ของ TCP

### 4.3 Acknowledgment (ACK)

**Acknowledgment** หรือ **ACK** คือการตอบรับที่ใช้แจ้งว่าข้อมูลในช่วงที่เกี่ยวข้องได้รับแล้ว

ตัวอย่างเชิงแนวคิด:

```text
ผู้ส่ง                                  ผู้รับ
  │                                       │
  ├──────────── ข้อมูล ──────────────────>│
  │<─────────── ACK ──────────────────────┤
```

ACK ช่วยให้ TCP ติดตามได้ว่าข้อมูลส่วนใดได้รับการยืนยันแล้ว หากข้อมูลสูญหาย TCP สามารถใช้กลไกตรวจจับและส่งซ้ำตามเงื่อนไขของโปรโตคอล

**ข้อควรจำ:** ACK ของ TCP ไม่ได้หมายความว่าผู้ใช้ปลายทางอ่านข้อมูลแล้ว หรือแอปพลิเคชันประมวลผลคำขอสำเร็จ แต่หมายถึงข้อมูลได้รับการยืนยันในระดับ TCP ตามขอบเขตที่ ACK นั้นระบุ

ตัวอย่างเช่น หากแอปส่งคำสั่งซื้อไปยัง Server แล้ว TCP ยืนยันว่าข้อมูลถึงระบบเครือข่ายของฝั่งรับ นั่นไม่ได้แปลว่าร้านรับคำสั่งซื้อ ทำอาหาร หรือจัดส่งเสร็จแล้ว แอปพลิเคชันต้องมีการตอบกลับระดับแอปพลิเคชันหากต้องการยืนยันสถานะเหล่านั้น

### 4.4 Sequence Number

TCP ใช้ **Sequence Number** เพื่อติดตามตำแหน่งของข้อมูลในกระแสข้อมูล (Byte Stream) ไม่ใช่เพียงใส่เลขกำกับ Packet เป็น 1, 2, 3 เท่านั้น

ตัวอย่างเชิงแนวคิด:

```text
ข้อมูลที่ส่ง:       [ช่วงข้อมูล A] [ช่วงข้อมูล B] [ช่วงข้อมูล C]
ตำแหน่งใน Stream:  ──────────────────────────────────────────>
```

Sequence Number ใช้ระบุตำแหน่งของไบต์ในกระแสข้อมูล ทำให้ TCP ตรวจจับข้อมูลที่ขาดหาย จัดการข้อมูลที่มาถึงไม่เรียงลำดับ และส่งข้อมูลให้แอปพลิเคชันในลำดับที่ถูกต้องได้

ตัวอย่างง่าย ๆ คือ หากข้อมูลบางช่วงยังมาไม่ถึง TCP สามารถรู้ได้ว่ามีช่องว่างในลำดับ และใช้กลไกการส่งซ้ำเพื่อช่วยกู้คืนข้อมูลนั้น

**จุดที่ต้องระวัง:** Sequence Number ของ TCP นับตำแหน่งเป็นไบต์ ไม่ใช่หมายเลข Packet โดยตรง และ ACK มักระบุหมายเลขไบต์ถัดไปที่ผู้รับคาดว่าจะได้รับ

### 4.5 TCP ทำให้การส่งข้อมูลน่าเชื่อถือขึ้นอย่างไร?

กลไกสำคัญของ TCP ได้แก่:

- **Sequence Number** — ติดตามตำแหน่งข้อมูลใน Byte Stream
- **Acknowledgment (ACK)** — ยืนยันข้อมูลที่ได้รับ
- **Retransmission** — ส่งข้อมูลซ้ำเมื่อพบหรือสงสัยว่าข้อมูลสูญหายตามกลไกของ TCP
- **Reordering** — จัดการข้อมูลที่มาถึงไม่เรียงลำดับ เพื่อส่งให้แอปพลิเคชันตามลำดับ
- **Flow Control** — ช่วยป้องกันไม่ให้ผู้ส่งส่งข้อมูลเร็วจนผู้รับรองรับไม่ไหว
- **Congestion Control** — ปรับการส่งเพื่อช่วยควบคุมความแออัดของเครือข่าย

ด้วยกลไกเหล่านี้ TCP จึงให้การส่งข้อมูลแบบเชื่อถือได้ (Reliable, ordered byte stream) มากกว่า UDP

อย่างไรก็ตาม TCP ไม่สามารถรับประกันว่าจะส่งสำเร็จในทุกสถานการณ์ หากเครือข่ายหรือปลายทางขาดการติดต่อเป็นเวลานาน การเชื่อมต่ออาจล้มเหลวได้ และแอปพลิเคชันต้องจัดการข้อผิดพลาดนั้น

| ชื่อเต็ม                     | Transmission Control Protocol       | User Datagram Protocol                                       |
| รูปแบบ                       | Connection-oriented                 | Connectionless                                               |
| ตั้งการเชื่อมต่อก่อนส่ง      | มี Three-way Handshake              | ไม่ต้อง                                                      |
| ยืนยันการรับด้วยโปรโตคอล     | มี ACK                              | ไม่มี ACK ในตัว UDP                                          |
| ส่งซ้ำเมื่อข้อมูลสูญหาย      | มีตามกลไก TCP                       | แอปพลิเคชันต้องทำเองหากต้องการ                               |
| จัดลำดับข้อมูลให้แอปพลิเคชัน | มี                                  | ไม่มี                                                        |
| การติดตามสถานะการส่ง         | มีสถานะการเชื่อมต่อ                 | UDP เองไม่ติดตามการส่งแบบ TCP                                |
| Overhead                     | โดยทั่วไปมากกว่า                    | โดยทั่วไปน้อยกว่า                                            |
| เหมาะกับงาน                  | งานที่ต้องการข้อมูลครบและเรียงลำดับ | งานที่ต้องการความเรียบง่ายและยอมรับการสูญหายหรือจัดการเองได้ |

### ตัวอย่างการใช้งานโดยทั่วไป

- **TCP:** เว็บผ่าน HTTP/HTTPS, การรับส่งไฟล์ และการเชื่อมต่อที่ต้องการข้อมูลครบถ้วนและเรียงลำดับ
- **UDP:** DNS บางรูปแบบ, การสื่อสารเสียง/วิดีโอแบบเรียลไทม์ และเกมออนไลน์บางประเภท

การเลือกใช้จริงขึ้นอยู่กับโปรโตคอลและการออกแบบของแอปพลิเคชัน บางงานที่ใช้ UDP อาจเพิ่มการยืนยันหรือกลไกความน่าเชื่อถือไว้ในระดับแอปพลิเคชันเอง

### Overhead คืออะไร?

**Overhead** คือข้อมูลและงานเพิ่มเติมที่จำเป็นเพื่อให้การสื่อสารทำงานได้ เช่น:

- การแลกเปลี่ยนข้อความเพื่อเริ่ม TCP Connection
- การส่ง ACK
- การติดตาม Sequence Number และสถานะของการเชื่อมต่อ
- การส่งข้อมูลซ้ำเมื่อจำเป็น

จึงไม่ควรจำแค่คำว่า “UDP เร็วกว่า TCP” แบบตายตัว ประเด็นสำคัญคือ TCP มีการจัดการเพิ่มเติมเพื่อความน่าเชื่อถือ ส่วน UDP มีหน้าที่น้อยกว่าและให้แอปพลิเคชันควบคุมพฤติกรรมเพิ่มเติมเองได้

## 6. Port Number — ข้อมูลไปถึงเครื่องแล้ว ต้องส่งให้โปรแกรมไหน?

IP Address ช่วยระบุเครื่องปลายทาง แต่ในเครื่องเดียวกันอาจมีโปรแกรมหลายตัวใช้เครือข่ายพร้อมกัน จึงต้องมี **Port Number** เพื่อช่วยระบุจุดรับส่งของโปรแกรมหรือบริการภายในเครื่อง

เปรียบเทียบกับองค์กร:

```text
หมายเลขโทรศัพท์หลัก → ติดต่อองค์กร
หมายเลขต่อ          → ติดต่อแผนกภายในองค์กร

IP Address          → ติดต่อเครื่อง
Port Number         → ระบุจุดรับส่งของโปรแกรม/บริการในเครื่อง
```

Port Number เป็นตัวเลขในส่วนหัวของ TCP หรือ UDP **ไม่ใช่ช่องเสียบสายบน Router หรือ Switch**

ตัวอย่างเช่น:

- **TCP Port 80** มักใช้กับ HTTP
- **TCP Port 443** มักใช้กับ HTTPS

หมายเลขพอร์ตเป็นเพียงตัวบ่งชี้ตามการกำหนดหรือการใช้งานทั่วไป การเห็นพอร์ต 80 เพียงอย่างเดียวไม่ได้พิสูจน์ว่า Payload ภายในเป็น HTTP จริง และบริการอาจกำหนดให้ใช้พอร์ตอื่นได้

### ทำไมต้องแยก TCP Port กับ UDP Port?

TCP และ UDP มีพื้นที่หมายเลขพอร์ตแยกจากกัน ดังนั้นหมายเลขเดียวกัน เช่น 53 อาจถูกใช้ทั้งใน TCP และ UDP ได้ โดยไม่ได้หมายถึง Endpoint เดียวกันโดยอัตโนมัติ

---

## 7. Socket คืออะไร?

ในคำอธิบายพื้นฐาน **Socket Endpoint** สามารถมองได้จาก:

```text
IP Address + Port Number
```

ตัวอย่าง:

```text
192.168.1.50:55555
```

หมายถึง Endpoint ที่ใช้ IP Address `192.168.1.50` และ Port `55555`

คำว่า Socket มีความหมายทางเทคนิคมากกว่าการนำ IP กับ Port มาบวกกัน แต่สำหรับการเริ่มเรียนเรื่องการระบุจุดรับส่ง การมองเป็น **IP:Port** เป็นแบบจำลองที่มีประโยชน์

---

## 8. ทำไม TCP Connection ต้องใช้ข้อมูล 4 อย่าง (4-Tuple)?

สมมติคอมพิวเตอร์ของผู้ใช้เปิดเว็บเบราว์เซอร์สองแท็บและเชื่อมต่อไปยัง Server เดียวกันผ่าน HTTPS ที่ Port 443 ทั้งสองการเชื่อมต่ออาจมีปลายทางเหมือนกัน:

```text
Server IP:443
```

แต่ Server ยังต้องรู้ว่าข้อมูลที่ส่งกลับควรเป็นของการเชื่อมต่อใด เพราะแต่ละการเชื่อมต่อมาจาก Endpoint ต้นทางคนละชุด

TCP ใช้ข้อมูล 4 อย่าง หรือ **4-Tuple** เพื่อระบุการเชื่อมต่อ:

1. **Source IP Address** — IP ต้นทาง
2. **Source Port** — พอร์ตต้นทาง
3. **Destination IP Address** — IP ปลายทาง
4. **Destination Port** — พอร์ตปลายทาง

ตัวอย่าง:

```text
การเชื่อมต่อที่ 1:
192.168.1.50:50001  ↔  203.150.x.x:443

การเชื่อมต่อที่ 2:
192.168.1.50:50002  ↔  203.150.x.x:443
```

ในตัวอย่างนี้ Source Port ต่างกัน จึงช่วยแยกการเชื่อมต่อทั้งสองได้ แม้ปลายทางจะเป็น IP และ Port เดียวกันก็ตาม ระบบปฏิบัติการมักเลือก Ephemeral Port ให้กับการเชื่อมต่อฝั่ง Client

ในเครือข่ายจริง NAT อาจเปลี่ยน IP Address หรือ Port ระหว่างทางได้ แต่หลักการที่ปลายทางใช้ข้อมูลของคู่การสื่อสารเพื่อแยก Connection ยังคงสำคัญ

**ข้อควรจำ:** 4-Tuple เป็นตัวระบุการเชื่อมต่อ TCP ในบริบทนี้ ไม่ได้หมายความว่าคนอื่นจะเข้ามาแทรกไม่ได้โดยสมบูรณ์ การป้องกันความปลอดภัยต้องอาศัยกลไกอื่นเพิ่มเติม เช่น TLS และการยืนยันตัวตนตามความเหมาะสม

## 9. Session ไม่ใช่สิ่งเดียวกับ TCP Connection

ควรแยกคำสองคำนี้:

- **Session:** ชุดการติดต่อหรือบริบทการทำงานที่แอปพลิเคชันจัดการ เช่น การเข้าสู่ระบบหรือการทำธุรกรรมหลายขั้นตอน
- **TCP Connection:** การเชื่อมต่อระดับ TCP ที่มีสถานะการรับส่งข้อมูลระหว่าง Endpoint

แอปพลิเคชันอาจสร้าง Session ขึ้นมาได้โดยใช้ TCP หรือ UDP ก็ได้ ขึ้นอยู่กับการออกแบบของระบบ

UDP เองไม่ติดตามการส่งข้อมูลด้วยสถานะและการยืนยันแบบ TCP แต่ไม่ได้แปลว่าโปรแกรมที่ใช้ UDP จะจดจำข้อมูลจากข้อความก่อนหน้าไม่ได้ โปรแกรมสามารถเก็บสถานะของตนเองและเชื่อมโยง Datagram หลายชุดเข้าด้วยกันได้

นอกจากนี้ UDP ไม่ได้บังคับว่าทุกข้อความต้องมีการตอบกลับ บางงานส่งข้อมูลทางเดียวได้ ส่วนงานอื่นอาจออกแบบให้มีข้อความตอบกลับตามความต้องการ

## 10. Multiplexing — เครื่องเดียวใช้หลายบริการพร้อมกันได้อย่างไร?

**Multiplexing** ในบริบทของ Transport Layer คือการใช้ข้อมูลในส่วนหัว เช่น Protocol และ Port Number เพื่อแยกข้อมูลจากแอปพลิเคชันหลายตัวที่ใช้เครือข่ายร่วมกัน

ตัวอย่างเช่น คอมพิวเตอร์เครื่องเดียวอาจใช้เบราว์เซอร์ ประชุมออนไลน์ และเล่นเกมพร้อมกัน ระบบปฏิบัติการจะใช้ข้อมูลที่เกี่ยวข้องกับการเชื่อมต่อหรือ Socket เพื่อส่งข้อมูลที่รับเข้ามาให้โปรแกรมที่ถูกต้อง

ภาพรวมการระบุปลายทาง:

```text
IP Address     → เครื่องไหน?
TCP หรือ UDP   → ใช้โปรโตคอล Transport ใด?
Port Number    → จุดรับส่ง/บริการใดในเครื่อง?
4-Tuple        → TCP Connection ชุดไหน?
```

Multiplexing ไม่ได้หมายความว่าทุกโปรแกรมมีสายกายภาพแยกกัน แต่เป็นการจัดการข้อมูลหลายชุดผ่านทรัพยากรเครือข่ายร่วมกัน

## 11. สรุปภาพรวมการส่งข้อมูล

```text
Application Data
       │
       ▼
Transport Layer
  ┌───────────────┐
  │ TCP หรือ UDP  │  ← Port Number
  └───────────────┘
       │
       ▼
Network Layer
  ┌───────────────┐
  │      IP       │  ← Source/Destination IP
  └───────────────┘
       │
       ▼
Data Link Layer
  ┌───────────────┐
  │ Ethernet ฯลฯ  │  ← MAC Address ในลิงก์ที่เกี่ยวข้อง
  └───────────────┘
       │
       ▼
Physical Layer
   สัญญาณผ่านสื่อจริง
```

เมื่อส่งข้อมูล แต่ละ Layer จะเพิ่มข้อมูลกำกับตามหน้าที่ของตน กระบวนการเพิ่มข้อมูลกำกับนี้เรียกว่า **Encapsulation** เมื่อถึงปลายทาง แต่ละ Layer จะประมวลผลข้อมูลส่วนที่เกี่ยวข้องและส่งต่อขึ้นไปยัง Layer ที่สูงกว่า

## 12. สิ่งที่ต้องจำ

1. **IP เป็น Connectionless** และไม่ได้รับประกันว่าข้อมูลจะถึงครบหรือมาถึงตามลำดับเดิม
2. **TCP เป็น Connection-oriented** มี Three-way Handshake, Sequence Number, ACK และกลไกส่งซ้ำเพื่อช่วยให้ข้อมูลได้รับครบและเรียงลำดับ
3. **UDP เป็น Connectionless** ส่งได้โดยไม่ต้องตั้ง Connection ก่อน และตัว UDP ไม่มี ACK หรือการส่งซ้ำให้อัตโนมัติ
4. **ACK ยืนยันการรับในระดับ TCP** ไม่ได้ยืนยันว่าแอปพลิเคชันประมวลผลสำเร็จหรือผู้ใช้เปิดอ่านแล้ว
5. **Sequence Number ของ TCP ระบุตำแหน่งไบต์ใน Byte Stream** ไม่ใช่หมายเลข Packet แบบตรง ๆ
6. **Port Number ช่วยแยกจุดรับส่งของแอปพลิเคชัน** ส่วน IP Address ใช้ระบุเครื่องปลายทาง
7. **Socket Endpoint มองเบื้องต้นเป็น IP:Port**
8. **TCP Connection แยกได้ด้วย 4-Tuple:** Source IP, Source Port, Destination IP และ Destination Port
9. **Session กับ TCP Connection เป็นคนละแนวคิด** แอปพลิเคชันที่ใช้ UDP ก็สามารถจัดการ Session ของตนเองได้
10. **Overhead** คือข้อมูลและงานเพิ่มเติมที่ใช้ในการตั้งการเชื่อมต่อ ยืนยันการรับ ติดตามสถานะ และส่งซ้ำเมื่อจำเป็น

### จำแบบสั้นที่สุด

- **IP:** พยายามส่ง Packet ไปยัง IP ปลายทาง
- **UDP:** ส่ง Datagram โดยไม่ตั้ง Connection และไม่ติดตามการรับให้เอง
- **TCP:** ตั้ง Connection และติดตามข้อมูล เพื่อส่งมอบ Byte Stream ที่ครบถ้วนและเรียงลำดับเมื่อการเชื่อมต่อทำงานได้
- **Port:** ช่วยระบุจุดรับส่งของโปรแกรม
- **4-Tuple:** ช่วยระบุ TCP Connection แต่ละชุด
